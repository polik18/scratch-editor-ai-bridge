# Scratch AI Bridge 改善計畫：讓小模型用簡單方法做出複雜作品

日期：2026-11-10。狀態：規劃，尚未實作。適用 source：`packages/scratch-ai-bridge`（本工作樹 HEAD `655584e588`）。

## 1. 目標

讓 7B 等級的本機小模型，只靠簡短輸入與少量回合，就能做出**多角色、多規則、多關卡**且**實際可玩**的 Scratch 作品，不限於特定遊戲類型。

原則：**把難度從模型移到工具。**模型只負責「要什麼」（實體、行為、規則、版面），Bridge 負責「怎麼做到」（積木、物理、執行時序、碰撞、素材、驗證）。複雜度來自**組合許多簡單、已驗證的零件**，不是要求模型寫出複雜程式。

不做：為每種遊戲寫固定模板；把小模型換成大模型；取代現有 Canonical IR（它保留為底層與逃生口）。

## 2. 現況與問題（有證據的部分）

| 觀察 | 證據 |
|---|---|
| AI 必須直接輸出 Canonical IR 積木樹 | 唯一生成入口是 Canonical IR／GameDesign JSON；GameDesign（`src/core/ir/design-interface.ts`）仍是逐一 opcode。 |
| 輸出量大 | 2026-11-10 實作一個原創平台遊戲（7 角色）需 245 積木、IR 約 60 KB；小模型很難一次寫對這個量。 |
| 提示詞已不小 | 學生生成提示約 5.9k 字元（估 2k token）；完整 authoring 指令約 12.3k 字元（估 3.7k token）。130 個 opcode 規則全部放進上下文。 |
| 編譯通過 ≠ 可玩 | 同一遊戲 13 道 gate 一次全過，但仍有 3 個玩法錯誤（跳不上平台、無敵時掉坑不扣命等），全靠另寫的劇本式試玩才抓到；生成報告的 `runtime-behavior` 固定為 `not-run`。 |
| 正確寫法需要 Scratch 專業知識 | 碰撞推出、`warp` 自製積木避免逐格執行、跨角色用旗標而非廣播避免重入等，模型不知道就會寫出「能編譯但不能玩」的程式。 |
| 修復只到格式／語意層 | `src/core/repair`、`validator/semantic.ts` 修 JSON 形狀與引用；沒有「遊戲意義」的檢查（可達性、數值合理性）。 |
| 試玩只檢查通用移動 | `src/core/playtest/feedback.ts` 判斷按鍵是否讓某角色移動、變數是否改變；不知道作品「應該」發生什麼。 |
| MCP 工具粒度粗 | `src/mcp/tools.ts` 只有 inspect 與整份 `propose_live_patch`；沒有「加一個角色」「加一條規則」等小步驟。 |
| 尚無小模型數據 | `docs/bridge-ai-tasks/P5-model-evaluation.md` 真實模型評估未執行；2026-11-05 goboscript 比較（G0d）因無數據以 not-adopt 結案。 |

已有可直接沿用的資產：Canonical IR 與官方 VM 編譯 gate、capability registry、自動素材（`visuals`）、repair 報告、scratchblocks 文字解析器（`src/core/scratchblocks/parser.ts`）、預覽頁的按鍵／狀態擷取協定（`src/preview/main.ts` 的 `playtest-key`、`capture-game-progress`）、`PlaytestRunner`、MCP relay 與待審 patch 流程。

## 3. 設計：五個支柱

### 支柱 A：行為元件庫（Behavior Library）

一個**行為**是可參數化、已驗證的能力包，掛在角色上即可運作。每個行為都包含：

1. **參數 schema**：少量欄位，全部有預設值與白話等級（如 `速度: 慢/中/快`），數值由行為自行換算。
2. **積木實作**：人寫、測過的 Canonical IR 片段（必要時用 `warp` 自製積木），命名清楚、附中文註解，學生打開 Scratch 仍讀得懂。
3. **契約**：會讀寫的狀態（例如 `onGround`、`生命`）、會發出的事件（`被收集`、`被踩扁`、`抵達`），以及與其他行為的相容性。
4. **自動試玩劇本**：例如「平台移動」自動驗證左右移動、跳高、落地不穿透；「收集品」驗證碰到會消失並觸發事件。
5. **靜態檢查**：例如依跳躍等級和重力，算出可跳上的高度。

初版目標是約 25 個**跨類型**行為，分四類：

- **移動**：平台移動、俯視移動（四方向／八方向）、格子移動、跟隨目標、來回巡邏、沿路徑移動、拋射物、滑鼠拖曳／點擊。
- **互動**：收集品、危險物、可踩扁、終點、門與鑰匙、可推箱子、生成器（定時產生分身）、對話者、問答者。
- **狀態**：分數、生命、計時器、背包、血量條、關卡（場景）切換。
- **呈現**：鏡頭捲動、造型動畫、音效回饋、提示文字。

類型不是模板，而是行為的組合：平台遊戲 = 平台移動 + 可踩扁 + 收集品 + 終點；迷宮 RPG = 俯視移動 + 門與鑰匙 + 對話者 + 背包；射擊 = 八方向 + 拋射物 + 生成器 + 血量。新玩法要新增的是行為，不是新增一種遊戲類型。

### 支柱 B：精簡作品描述（Game Spec）

在 Canonical IR 之上新增一層小而寬容的描述格式。模型要寫的只有四件事：

```yaml
作品: 森林鑰匙迷宮
場景:
  - 名稱: 第一關
    地圖: |          # 選用；空間性作品用文字格子，非空間作品可省略
      ##########
      #P..o..#K#
      #.###..#.#
      #...N..D.#
      #####..#G#
    圖例: { P: 主角, o: 金幣, K: 鑰匙, D: 門, N: 老爺爺, G: 出口, "#": 牆 }
角色:
  主角:   { 行為: [俯視移動: {速度: 中}] }
  金幣:   { 行為: [收集品: {分數: 10}] }
  鑰匙:   { 行為: [收集品: {放進背包: 鑰匙}] }
  門:     { 行為: [門: {需要: 鑰匙}] }
  老爺爺: { 行為: [對話者: {台詞: ["鑰匙在右上角喔！"]}] }
  出口:   { 行為: [終點] }
規則:
  - 當 主角 收集 金幣 → 播放 叮
  - 當 分數 ≥ 30 → 顯示 "找到所有金幣！"
  - 當 主角 抵達 出口 → 進入 第二關
```

設計要點：

- **規則用「當…→…」**：事件來自行為契約，動作來自少量白名單（改變數、播放、顯示、切換場景、生成、勝利、失敗）。這是組合出複雜度的主要手段。
- **格式寬容**：中英文鍵、等級詞與數字都接受；拼錯的名稱用最接近的候選自動修正並回報。沿用現有 repair 的做法，但是在 Spec 層進行。
- **逃生口**：行為做不到的部分，允許在角色下寫 `腳本:`，用 **scratchblocks 文字**（已有解析器，比 IR JSON 短很多，網路上也有大量訓練資料）。只有最後才退回 Canonical IR。
- **可往返**：Spec 隨 SB3 存一份，內容 hash 寫在專案註解或中繼資料。之後修改仍在 Spec 層進行；若使用者在 Scratch 手動改過、hash 對不上，就明確降級到既有的 IR／raw patch 流程，不猜測。

### 支柱 C：編譯器承擔難度

`Game Spec → Canonical IR → 既有 gate`。編譯器負責：

- 把地圖格子轉成座標與造型。牆和地面合併成單一碰撞角色，同類物件用分身產生（今天的金幣做法）。
- 產生「看起來簡單、其實難寫對」的部分：主迴圈、`warp` 物理、跨角色旗標、初始化與重開、場景切換時的清理。
- 名稱解析與自動素材（沿用 `visuals`）。
- **遊戲意義檢查**（新）：終點可達、平台可跳上、鑰匙在門之前取得得到、規則引用的事件存在、數值合理（例如生命 0、速度大到穿牆）。每一條都附**可直接套用的修正建議**。

### 支柱 D：小步驟、即時回饋的工具介面

小模型不擅長一次寫出整份作品，但擅長「做一小步、看結果、再一小步」。在 CLI 和 MCP 提供以 Spec 為單位的小工具，每次呼叫都會立刻驗證，並回傳精簡的現況：

| 工具 | 作用 |
|---|---|
| `list_behaviors(關鍵字)` | 依需求檢索相關行為卡（只回傳相關的幾張，不全部丟給模型） |
| `add_entity` / `attach_behavior` / `set_param` | 加角色、掛行為、改參數 |
| `edit_map` | 改地圖的某幾列 |
| `add_rule` / `remove_rule` | 管理「當…→…」 |
| `build_and_playtest` | 編譯並執行自動試玩，回傳白話結果與修正建議 |
| `apply_fix(建議 id)` | 一鍵套用工具提出的修正 |
| `summary` | 目前作品摘要（≤ 1k token） |

與現有安全模型一致：網頁上的作品仍然是「候選 → 使用者確認」，MCP 不提供直接套用到使用者作品的工具。新工具只修改 Spec 草稿與預覽。

### 支柱 E：會說人話的自動試玩

- 試玩劇本**由行為契約自動產生**，模型和使用者都不用寫。把今天手寫的 `playtest.mjs` 做法通用化：用 `playtest-key` 送按鍵、用 `capture-game-progress` 讀狀態、再用簡單的自動玩家（朝目標移動，遇到危險就跳或閃避）嘗試過關。
- 結果用白話表達，並對應回 Spec 位置：「第 2 列的平台比跳躍高度高 1 格（行為 平台移動.跳躍=中）→ 建議改成『高』或降低平台」。
- 結果分成 pass／fail／not-run，延續專案現有的證據紀律，不把編譯成功說成可玩。

## 4. 分階段計畫

每個階段都要附可重播的證據（命令、退出碼、成功數／總數）；依 `AGENTS.md` 先寫失敗測試，再實作。

### S0：小模型基準（先量測，再改）

- 建立約 20 題的跨類型作品需求集（平台、俯視迷宮、射擊、接物、問答、故事對話、模擬、多關卡），分簡單／中等／複雜三級。每題都附人寫的**驗收劇本**。
- 用使用者允許的本機小模型（1 至 2 個 3B–8B 等級，固定版本與參數），透過現有 OpenAI 相容介面跑**現行路徑**（學生提示 → IR → repair → 編譯），每題 3 輪修正預算。
- 指標：首輪可編譯率、3 輪內可編譯率、驗收劇本通過率、輸入／輸出 token、回合數、主要失敗類型。
- **驗收**：基準報告可重播；沒有模型時標 not-run，但需求集與劇本照樣完成。這同時補上 P5 和 G0 缺少的數據。

### S1：Spec v0 與核心行為

- 定義 Spec schema、寬容解析器與錯誤訊息；先做 8 個行為（平台移動、俯視移動、來回巡邏、收集品、危險物、可踩扁、終點、分數／生命），規則白名單，以及 scratchblocks 逃生口。
- 用今天的平台遊戲當第一份行為來源，整理成可參數化的片段。
- **驗收**：每個行為都有單元測試與 VM 編譯 gate；人寫的 Spec 可重現今天的遊戲；行為兩兩組合沒有變數或廣播衝突。

### S2：遊戲意義檢查與自動試玩

- 行為契約 → 靜態檢查與試玩劇本；通用自動玩家；白話診斷與 `apply_fix`。
- **驗收**：故意埋入的錯誤（平台過高、終點封死、鑰匙在門後、規則引用不存在的事件）全部被指出並附修正建議；今天實測抓到的 3 個問題可以自動重現並被偵測。

### S3：小步驟工具與網頁流程

- CLI 子命令，以及 MCP 的 Spec 工具（支柱 D）；`list_behaviors` 依關鍵字檢索行為卡；`summary` 限制大小。
- 學生網頁：保留現有「貼回 AI 回覆」流程，新增「Spec 模式」：提示詞只附相關行為卡，AI 回 Spec，Bridge 自動編譯、試玩、顯示白話結果。
- **驗收**：提示詞 ≤ 3k token、典型 Spec 輸出 ≤ 1.5k token；MCP 協定測試涵蓋過期 revision、待審候選不被覆蓋、斷線等情況。

### S4：擴充到約 25 個行為與多場景

- 補齊支柱 A 清單、場景切換、鏡頭捲動、背包、對話、問答。
- **驗收**：S0 需求集每一題都能用 Spec 表達（不需要逃生口的比例要記錄）；行為兩兩組合測試矩陣通過。

### S5：小模型實測與調整

- 以 S0 相同模型、預算和題目，跑 Spec 路徑（一次輸出與 MCP 小步驟兩種方式），與基準比較。
- 依失敗類型調整：行為卡寫法、寬容解析、預設值、修正建議措辭。
- **成功標準（暫定，依 S0 結果校正）**：7B 等級模型在 3 輪內，驗收劇本通過率比基準提高至少一倍，而且中等難度題目達到 70% 以上；輸出 token 中位數下降 80% 以上。

## 5. 風險與對策

| 風險 | 對策 |
|---|---|
| 行為庫不夠用，模型被卡住 | scratchblocks 逃生口；記錄逃生口使用率，作為新增行為的優先順序依據 |
| 行為組合時互相干擾 | 契約宣告讀寫的狀態；兩兩組合矩陣測試；命名空間化變數 |
| 產生的積木難讀，失去教學價值 | 行為輸出使用有意義的自製積木名稱與註解；教師版提供「這個行為怎麼做到」的說明 |
| Spec 與 SB3 不同步 | hash 綁定；不一致就降級到 IR／raw patch，並明確告知使用者 |
| 自動玩家過不了關，不一定代表遊戲有問題 | 回報為「自動玩家未過關」並附軌跡，不直接判定為失敗；劇本可由關卡作者補充路徑提示 |
| 指標好看但不好玩 | S0／S5 除了自動劇本，抽樣做真人試玩，標註為真人證據 |

## 6. 第一批工作（建議順序）

1. S0 需求集與驗收劇本的格式（不需要模型即可完成）。
2. 把 `PlaytestRunner` 擴充成可執行劇本（送按鍵序列、斷言狀態），這是 S0、S2 和 S5 共同的基礎。
3. Spec schema 草案與 3 個行為（平台移動、收集品、終點）的端到端雛形：Spec → IR → gate → 自動試玩。
4. 若有可用的本機小模型，跑 S0 基準；沒有則標 not-run，繼續進行 S1。
