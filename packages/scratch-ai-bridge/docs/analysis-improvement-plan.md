# 作品分析改善計畫

**狀態**：2026-11-01 起始版本  
**目標**：提升 Bridge 對 Scratch 作品的靜態分析準確度、回饋可用性與學生理解度  
**範圍**：分析模組、回饋生成、診斷報告、學生導向提示

---

## 一、現狀盤點與問題診斷

### 1.1 分析模組狀態

| 模組                   | 狀態 | 問題                                                              |
| ---------------------- | ---- | ----------------------------------------------------------------- |
| `src/core/analyzer.ts` | 完成 | 7類規則已實作，但缺少擴充性與可測試性                             |
| `src/core/repair.ts`   | 完成 | 回饋提示可讀性不足，缺少學生導向語氣                              |
| `src/core/prompt.ts`   | 完成 | 分析提示與評分提示已分離，但學生用提示未明確標記                  |
| `src/cli/inspect.ts`   | 完成 | CLI 可輸出 json/markdown/student-markdown，但預設格式对学生不友善 |

### 1.2 回饋品質問題

| 問題             | 範例                                       | 影響                       |
| ---------------- | ------------------------------------------ | -------------------------- |
| 技術術語過多     | `undefined variable 'score'`               | 學生看不懂變數未宣告的意義 |
| 缺少具體修正指引 | `block not supported`                      | 學生不知如何修正           |
| 缺少情境關聯     | 舞台變數警告未說明「為何學生會用舞台變數」 | 學生不理解問題與作品的關係 |
| 缺少正向鼓勵     | 全是警告與錯誤                             | 學生易受挫，放棄修復       |

### 1.3 診斷報告缺失

| 項目     | 狀態                               |
| -------- | ---------------------------------- |
| 可重現性 | 某些診斷缺少最小可複現案例         |
| 聚合性   | 多個診斷未自動合併為「主題式警告」 |
| 優先級   | 所有診斷平等顯示，未標示緊急度     |

## 二、改善目標與優先級

### 2.1 P0：學生導向診斷語氣（1-2 天）

**目標**：每則診斷使用「觀察 → 影響 → 建議」結構，並加入學生可理解的比喻

**規則**：

- 避免術語：用「積木的輸入插槽」代替「block input」
- 加入比喻：「變數像小倉庫，要先造倉庫才能放貨」
- 每則診斷包含：`[學生可理解標題]` + `[原因]` + `[影響]` + `[怎麼辦]`

**輸出**：

```
[觀察] 你有一個變數叫「score」，但沒有先建立這個變數
[影響] 當積木想要「增加 score 1」時，Scratch 不知道該改哪個值
[怎麼辦] 點擊舞台左下角「建立變數」→ 輸入「score」→ 選「所有角色」
```

### 2.2 P1：診斷聚合與主題化（1-2 天）

**目標**：將分散的診斷自動歸類為「主題式警告」，減少學生 overwhelm

**規則**：

- `missing-assets` → 「素材遺失」主題
- `undefined-variable` → 「變數問題」主題
- `unsupported-block` → 「特殊積木」主題
- 每個主題顯示：「共 X 個相關問題：1. ... 2. ...」

**輸出**：

```
📊 可能的問題（3 個相關項目）
├─ 🎨 素材遺失（2 個）
│  ├─ 舞台缺少「background.png」
│  └─ 角色「cat」缺少「costume2.png」
└─ 🔤 變數問題（1 個）
   └─ 變數「score」未宣告，無法使用
```

### 2.3 P2：診斷優先級與緊急度（1 天）

**目標**：標示「高/中/低」緊急度，讓學生知道先修哪個

**規則**：

- **高**：影響作品能否載入（missing assets, broken graph）
- **中**：影響功能但作品仍可運作（unsupported block, warning）
- **低**：建議改進但非必需（performance, best practice）

**輸出**：

```
⚠️ 2 個高優先問題（作品可能無法正常運作）
✓ 1 個低優先建議（改進後會更好）
```

## 三、技術改善項目

### 3.1 建立 Diagnostic Catalog（P0）

**目標**：將 7 類診斷擴充為可擴充的分類系統

**做法**：

1. 建立 `src/core/diagnostics/catalog.ts` 定義 `DiagnosticType` enum 與 `DiagnosticCategory` enum
2. 建立 `src/core/diagnostics/messages.ts` 存放學生導向提示模板
3. 建立 `src/core/diagnostics/aggregator.ts` 負責聚合與主題化

**檔案**：

```
src/core/diagnostics/
├── catalog.ts      # 類型與分類定義
├── messages.ts     # 提示模板（中英雙語）
├── aggregator.ts   # 聚合與主題化
└── format.ts       # CLI 與 Web 輸出格式
```

### 3.2 學生導向提示模板庫（P0）

**目標**：100 個常見問題的學生可用提示（分 10 類，每類 10 個）

**類別**：

1. 結構問題（缺少開始積木、腳本斷開）
2. 變數問題（未宣告、作用域錯誤）
3. 素材問題（遺失、格式不支援）
4. 積木問題（不支援、拼寫錯誤）
5. 邏輯問題（無限迴圈、條件錯誤）
6. 角色問題（不可見、位置錯誤）
7. 舞台問題（變數衝突、監視器位置）
8. 外部擴充（extension 未載入、硬體要求）
9. 語音/相機（需要授權、瀏覽器限制）
10. 最佳實踐（效能、可維護性）

**模板結構**：

```typescript
interface DiagnosticMessage {
  id: string; // e.g., "STRUCT_001"
  category: "structure" | "variable" | "asset" | ...;
  severity: "high" | "medium" | "low";
  title: string; // 學生可理解標題
  description: string; // 詳細說明（比喻 + 技術）
  impact: string; // 對作品的影響
  fix: string; // 具體步驟
  example?: string; // 修正前後對比
}
```

### 3.3 聚合與主題化引擎（P1）

**目標**：自動將分散診斷歸類為主題，減少學生認知負擔

**做法**：

1. 建立 `DiagnosticGroup` 介面：`category`、`severity`、`items: Diagnostic[]`
2. 建立 `aggregateDiagnostics()` 函數：依 `category` 與 `severity` 分組
3. 建立 `formatDiagnosticGroup()` 函數：生成主題式文字

**規則**：

- 相同 category + severity → 聚合為一個主題
- 每個主題顯示「共 X 個相關問題」
- 最多聚合 5 個子項目，超過顯示「+N 更多」

### 3.4 嚴重度標示與優先級（P2）

**目標**：讓學生知道「先修哪個問題」

**做法**：

1. 每則診斷標示 `severity: "high" | "medium" | "low"`
2. CLI 與 Web 報告顯示「高優先 X 個、中優先 Y 個、低優先 Z 個」
3. 預設排序：high → medium → low

## 四、CLI 與 Web 整合改善

### 4.1 CLI 命令改進（P0-P2）

**現狀**：

- `scratch-ai-bridge inspect`：輸出 json/markdown/student-markdown
- 預設 markdown 對學生不友善

**改善**：

1. 新增 `--severity-level` 參數：`all | high | high-medium`
2. 新增 `--group-by` 參數：`category | severity | none`
3. student-markdown 預設聚合 + 嚴重度排序

**範例命令**：

```bash
# 只看高優先問題，並依主題聚合
scratch-ai-bridge inspect project.sb3 --severity-level high --group-by category
```

### 4.2 Web UI 改善（P0-P2）

**現狀**：診斷以線性列表顯示，學生易迷失

**改善**：

1. 分區顯示：「問題」（高優先）、「建議」（低優先）
2. 關聯提示：點擊診斷顯示「這對我的作品有什麼影響？」
3. 修正指引：每則診斷提供「怎麼辦」按鈕，展開具體步驟

## 五、測試與驗收

### 5.1 測試策略

| 項目         | 方法                                              | 備註                 |
| ------------ | ------------------------------------------------- | -------------------- |
| 提示可讀性   | 邀請 5 位學生測試，問「你覺得這段提示在說什麼？」 | 不得有 >50% 學生誤解 |
| 聚合準確性   | 檢查 100 個診斷案例，確認歸類正確率 ≥ 95%         | 人工審核             |
| 嚴重度準確性 | 標註 50 個「高/中/低」案例，與教師判斷比對        | 一致性 ≥ 90%         |

### 5.2 驗收標準

**P0：學生導向診斷**

- ✅ 100 個常見診斷使用「觀察 → 影響 → 建議」結構
- ✅ 0 個診斷使用技術術語（如「variable」→「小倉庫」）
- ✅ 每則診斷包含具體修正步驟

**P1：診斷聚合**

- ✅ 80% 以上診斷能自動歸類為主題
- ✅ 主題式警告顯示「共 X 個相關問題」

**P2：優先級標示**

- ✅ 高/中/低標示與教師判斷一致性 ≥ 90%
- ✅ CLI 與 Web 預設依嚴格度排序
