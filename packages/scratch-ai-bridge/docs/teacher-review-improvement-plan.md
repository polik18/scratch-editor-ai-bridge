# 教師視角改善計畫

更新：2026-10-19；狀態：工程階段 0–5 已實作並完成本機驗證；Phase 6 真人教師盲評／學生可用性驗收未完成，因此 Phase 7 正式發布門檻未通過。此計畫以 Scratch 課堂中的形成性回饋為目標，不把 Bridge 的靜態分數當成學生能力或學期成績。

## 目標

學生上傳 `.sb3` 後，能看懂工具觀察到的程式線索，知道下一步去哪裡檢查，並能自行測試與修正。教師能辨認哪些結論有積木證據、哪些只是待確認問題、哪些因 extension 或靜態分析限制而無法判斷。

學生解惑頁維持單純：不顯示成績、不提供 AI 寫程式、不加回首頁連結。外部 AI 是可選的延伸協助；不使用外部 AI 的學生也要能拿到第一個可操作提示。

## 現況基線

- `student-help.html` 已提供本機 SB3 分析、學生提問、本機第一步提示、可複製外部 AI 提示與匿名作品線索地圖；以合成 SB3 瀏覽器 smoke 驗證三種瀏覽器都能顯示角色/腳本/積木位置與實際座標。
- evidence packet 已移除素材 bytes、原始 block ID、JSON path 與角色原名；學生取得隱私保護的同時，角色序號與內部 F/E 證據編號可能不利於回到 Scratch 找積木。
- `sb3-static-v2` 是依 SB3 結構固定計算的 100 分制，資料/互動面向未使用時標示不適用並從分母排除，尚未經教師校準。它不會執行作品，也不能衡量創意、手感、作者理解或學習歷程。
- 擴充積木目前只對照樣本常見的 10 個官方 opcode；未知第三方 extension 會保留並標示限制，不應被當成學生錯誤或扣分依據。
- 教師審閱表及 5 人學生可用性測試腳本已存在，尚未取得真人實測結果；不得將合成 fixture 或自動化 smoke 寫成教學驗收。
- 2026-10-19 本機 Bridge 測試 446/446、lint、build/bundle budgets、benchmark 及 Chromium/Firefox/WebKit browser smoke 通過。Bench 最慢項目為 4 MiB SB3 匯入平均 57.1 ms，低於 250 ms 預算；2000 blocks 編譯平均 8.0 ms，低於 75 ms 預算。GitHub Actions 最新狀態須以此次提交的 checks 為準。

## 執行階段

### Phase 0 — 恢復候選版本的綠燈

**工作**

1. 先檢查公開 check annotations；若 job log 因權限不可下載，依 workflow 順序本機重跑每個子步驟。
2. 本機重現顯示 444/444 tests 通過，Prettier 因 `extension-teacher-review.md` 格式不符失敗；格式修正後 lint、benchmark 和三瀏覽器 smoke 通過。推送後 run `38914081250` 的 Build 與 Bridge 套件工作通過，已確認根因修正。
3. 等 checks summary 完成並確認整體 workflow 成功，再更新支援矩陣與 status 記錄；不可只 rerun 隱藏失敗或把檢查改成非阻擋。

**驗收**：最新候選 SHA 的 Bridge CI、build、lint、benchmark、Chromium、Firefox、WebKit 全部成功，失敗 run 的根因和修正有紀錄。

### Phase 1 — 將 100 分限制為可解釋的「SB3 結構參考分」

**工作**

1. UI、CLI、Gemini 提示和報告統一稱作「SB3 結構參考分」，醒目說明不是正式學科成績，也不是程式實際運作品質。
2. 檢查現行公式中「沒有使用資料積木/互動積木就拿該項滿分」及按腳本比例計分的偏差。固定測試加入「綠旗後說你好」等最小專案；目前這類單一腳本可能得到 93 分，需避免高分暗示高品質。
3. 重訂可由 SB3 證明的評分錨點。不得因沒有變數、迴圈、廣播、多角色或特定遊戲功能扣分；不得因積木多、角色多而加分。
4. 對不適用或證據不足的項目標為 N/A/判讀有限，不自動給滿分。按適用面向配分換算 100 分；證據不足以計算時顯示「資料不足，暫不換算總分」。分項必須列出支持或扣分的 SB3 證據。
5. 以動畫、故事、藝術、單角色遊戲、多角色遊戲、含未知 extension 和部分損壞檔案測試各項描述，確認內容形式不會造成系統性偏差。

**2026-10-16 初步實作**：UI、CLI、評分 AI 提示已使用「SB3 結構參考分」；未使用資料或互動積木的面向標為「不適用」，不再自動取得滿分並按適用配分換算。沒有足夠可讀證據時不顯示總分。Bridge analyzer tests 446/446 通過；教師盲評尚未進行，因此仍是參考分，評分描述和權重未校準。

**驗收**：每個分項有可重現的四級描述與證據；不存在單純因「缺少某種積木」獲得滿分或扣分的規則；低 coverage 不輸出高確定性的總分；教師盲評完成前標示為暫定參考分。

### Phase 2 — 讓學生一眼找到分析依據

**工作**

1. 在學生解惑頁加入簡短作品地圖：例如「角色 A → 綠旗程式 → 定位積木（x=120、y=0）」。點選後能展開相關積木摘要。
2. 建立穩定的隱私別名（舞台、角色 A、角色 B），同一別名同時出現在頁面與複製提示中；不要將原始角色名、姓名、block ID 或 JSON path 放進外部提示。
3. AI 回答以學生可見的位置和積木文字/數值作為依據；學生專用提示不包含 F1/E1 等內部索引，避免它們出現在學生回答中。
4. 限制每次顯示的線索數量，優先列一個最相關腳本；大量作品提供搜尋/展開，不一次鋪滿所有積木。

**2026-10-19 工程驗證**：學生頁已加入白話線索清單，初始顯示最多 40 筆，按「舞台／角色 A…＋第幾段程式」分組，並可逐批展開；複製給 AI 的 evidence packet 採相同別名，且已移除 F/E 編號欄位。Chromium、Firefox、WebKit smoke 以包含 x=120 定位積木的合成 SB3 驗證頁面、第一步提示和複製提示一致顯示「角色 A・第 1 段程式」及積木數值，且不包含內部證據 ID。線索尚未依問題排序或搜尋；真人學生能否在 Scratch 編輯器中找到積木仍待 Phase 6 驗收。

**驗收**：新手能依提示在自己的作品中找到正確角色與積木；抽查 AI 提示中的角色別名、腳本位置及數值皆可回到頁面證據；unknown blocks 不會被配上猜測名稱。

### Phase 3 — 形成「看線索、做預測、試一次」的解惑循環

**工作**

1. 把回饋固定成三段：觀察到的積木、學生可以做的一個檢查、做完後應比較的現象。
2. 以「為什麼主角一開始就在右邊？」為回歸情境：若 evidence 可讀到初始 X 值，先引導學生預測方向並查看定位積木；沒有足夠證據時先詢問/說明限制，不指定任意新數字。
3. 增加可選的「我原本想看到／實際看到」欄位或幾個常見問題入口（角色位置、按鍵、碰撞、分數、聲音）；學生仍可只寫一句自己的問題。
4. AI 提示分層，每輪只給一個下一步；學生回報觀察後才提供下一層提示。不要一開始就改寫整份作品。
5. 對無法使用外部 AI 的情境，提供本機規則提示與「找老師一起看」出口；複製提示始終由學生主動觸發。

**2026-10-16 第一輪實作**：學生輸入問題後，頁面會依位置、按鍵、碰撞、分數或聲音等常見詞，從 Project Map 找到一個相符積木，提供一個定位步驟；找不到相符線索時明確說目前無法判斷並建議找老師，不會自行編造角色/積木。此為規則式初步引導，尚未完成預測回報與多輪提示，也未由學生試用驗證。

**驗收**：對固定問題集，回答不會超出 evidence；每個步驟可以由小學生照著操作，並含可觀察的結果；不會把靜態推論寫成已執行結果。

### Phase 4 — 教師可用、學生隱私安全的班級批次回饋

**工作**

1. CLI 批次輸出分成教師總覽及個別學生回饋；每份作品列出 `ok`／`partial`／`failed` 的具體原因、涵蓋率、可讀線索、限制與下一步。
2. 對外報告使用匿名作品 ID；姓名對照僅由教師在本機保存並選擇性套用到個別輸出。不要把學生名冊、原始檔名、作品素材或原始 SB3 自動送到 AI。
3. 明確區分「檔案讀取失敗」、「Bridge 不支援」、「作品結構疑慮」和「需要 Scratch/硬體實際確認」。不使用單一 `partial` 或總分代替原因。
4. 對輸出建立覆寫保護、錯誤逐檔隔離、匿名 manifest、檔案大小限制及可追蹤的 rubric 版本。

**驗收**：混合有效/損壞/未知 extension 的班級資料可逐檔完成；一份失敗不影響其他作品；姓名映射不出現在預設輸出；教師能依報告分辨工具限制與學生作品問題。

### Phase 5 — 擴充積木與自製積木的教學文字校準

**工作**

1. 先完成 `extension-teacher-review.md` 的白話名稱審閱；特別確認 Face/Video Sensing 文字只描述積木設定/讀值，不暗示相機已成功運作。
2. 以學生作品實際頻率決定是否擴充 catalog；每一項新增都要有 VM 來源、fixture、輸入值格式、coverage 和安全限制。
3. 對 handpose/mesh 等未知第三方積木只說明「保留但尚無法解讀」和原 Scratch 確認方法；procedure 格式錯誤指出實際不一致欄位，避免把技術 ID 丟給學生。
4. 任何 extension 未支援、runtime 未驗證或硬體不存在都不能當成作品品質扣分。

**驗收**：教師可接受的白話名稱達既有審閱門檻；教師與學生都能分辨 Bridge 看不懂和作品錯誤；AI 不主張未知積木的效果、不宣稱裝置已執行。

### Phase 6 — 教師盲評與學生可用性驗收

**工作**

1. 至少兩位教師獨立盲評多類型代表作品；依現有 feedback corpus 表記錄準確度、證據定位、可採取程度、語氣、誤報和漏報。
2. 使用既有 5 人可用性腳本，觀察學生能否上傳、找到積木、理解工具限制、採取建議並說出觀察結果；不以學生喜好問卷取代任務完成觀察。
3. 不記錄姓名、帳號、原始對話或未匿名作品到公開 repo；只保存匿名彙總和可重現問題。
4. 未達門檻的回饋先改寫/修正再重測；分歧與未涵蓋作品類型保留在報告中。

**驗收**：沿用 [feedback-corpus-review.md](./feedback-corpus-review.md) 和 [student-usability-plan.md](./student-usability-plan.md) 的量化門檻；未完成真人評閱前，不標示「教師校準完成」或「適合正式評分」。

### Phase 7 — 分階段發布與課堂導入

**工作**

1. 修正 Phase 0 CI 阻塞；完成教師/學生驗收後，更新支援矩陣、隱私說明、教師一頁指南與變更紀錄。
2. 先讓教師小規模試用，不將 AI 分數自動匯入成績簿；教師確認錯誤回饋及擴充限制說明後再擴大。
3. Pages 部署只從正式允許的分支/工作流程執行；部署後檢查實際 commit、學生網址、離線資源、Chromium/Firefox/WebKit 及原生 Safari 需要的驗收項目。

**完成定義**：最新正式版本 CI 全綠；教師校準與學生任務測試達標；支援範圍、判讀限制、資料流和 rollback 方法已公開；部署驗證與使用者回饋均有日期和版本紀錄。

## 建議執行順序

1. Phase 0：取得 Bridge 失敗 CI 的 log 並修復。
2. Phase 1：修正參考分的高分偏差與低涵蓋率呈現。
3. Phase 2–3：增加可定位的學生證據和一步一試的本機/AI 提示。
4. Phase 4–5：完善班級報告和 extension 白話說明。
5. Phase 6：教師盲評、學生可用性測試、依結果修正。
6. Phase 7：通過門檻後才正式發布和課堂導入。
