# 競賽規格能力計畫：讓工具能做出符合「游智盃」規定的遊戲與動畫

2026-11-11。範圍只限**程式能力**，不做任何一件參賽作品。以「與我『河』關？」30 個提案當需求來源，目標是讓
`spec`／`make`／MCP `make_game` 產出的 `.sb3` 自動符合競賽硬性規定，並由工具自己驗證。

## 1. 驗收目標

完成後，下面每一項都要由工具自動檢查並寫進報告，不靠人工判斷：

| 類別 | 競賽規定                                   | 工具要能做到                                                            |
| ---- | ------------------------------------------ | ----------------------------------------------------------------------- |
| 遊戲 | 關卡 ≤ 2                                   | 描述可寫 1–2 關；第一關過關自動進入第二關                               |
| 遊戲 | 開始前呈現規則與操作說明                   | 自動產生開場說明頁（標題、規則、操作鍵），按鍵後才開始                  |
| 遊戲 | 操作介面、明確過關與勝負條件               | 每關必須有過關條件，否則建置失敗；結束畫面顯示勝負與分數                |
| 遊戲 | 難度適中                                   | 自動試玩能通關（現有 bot）；報告列出通關所需時間與失誤容許度            |
| 動畫 | 60–180 秒                                  | 編譯時算出片長，超出範圍就建置失敗；試玩實際量測一次                    |
| 動畫 | 完整情節、開頭與結尾、至少一位主角         | 描述要有主角；自動加片頭標題卡與片尾卡                                  |
| 動畫 | 至少一次過場（換背景）                     | 場景 ≥ 2 且背景不同，否則失敗；過場加淡入淡出                           |
| 共同 | 素材僅限 Scratch 內建、CC 非商業、自創     | 每個造型、背景、音效都有來源紀錄；匯入的檔案必填授權                    |
| 共同 | 註明生成式 AI 的使用                       | 從 `_過程/` 自動整理 AI 使用紀錄草稿                                    |

## 2. 現況（程式事實）

- `src/spec/compile.ts` `compileGameSpec`：所有腳本都從 `event_whenflagclicked` 開始；勝負只有一組 `win`/`lose` 廣播，
  `banner` 顯示後 `stop all`。**沒有遊戲階段，因此做不出說明頁和第二關。**
- `src/spec/types.ts` `GameSpec`：只有一張 `map`；`Look` 是 14 種程式畫出的造型（`src/spec/looks.ts`）；
  背景只有 `sky`／`grass` 兩種；`sounds: []`。
- 規則動作只有 `分數／生命／時間／自訂計數 ±N、說、過關、失敗`，沒有問答、搬運、放置。
- `src/core/visuals/library.ts`：`resolveLibraryAssets`、`createScratchAssetFetcher`（含 md5 驗證與快取）、
  `matchLibrarySprite`，加上 `library-zh.ts` 的中文關鍵字（343 角色、85 背景、354 音效）**已存在**，
  但只有網頁和 benchmark 在用，Game Spec 沒有接上。
- `src/core/visuals/catalog.ts` `inspectProjectAssetProvenance`：已能列出作品素材來源。
- `src/spec/scenario.ts`：試玩能讀角色的 `x/y/visible/costume` 與變數，能按鍵、點擊、由 bot 走到終點；
  **讀不到舞台背景，也沒有時間軸紀錄**，所以無法驗證過場與片長。
- Canonical IR（`src/core/capabilities/registry.ts`）已支援換背景、說話幾秒、滑行、音效、詢問與回答等積木，
  所以新功能都可以編譯到現有 IR，沿用現有建置檢查（schema、VM 載入、存檔、重新載入）。

## 4. 設計原則

1. **舊描述照常可用。** 只有一張 `地圖`、沒有 `關卡` 的描述，就當成只有一關；現有 5 個範例和測試不改也要通過。
2. **一律編譯到 Canonical IR。** 不另寫 `.sb3` 產生器；新功能都走現有的建置檢查。
3. **給模型的說明分模式。** `guide game`、`guide story` 各自不超過約 1,000 token（用
   `scripts/bench/measure-game-prompt-budget.ts` 量），小模型一次只看一種格式。
4. **競賽規則寫成設定檔，不寫死在程式裡。** 例如 `src/contest/profiles/youzhi-2026.json`，明年規則改了只改設定檔。
5. **每個新功能都要有自動試玩。** 沒有試玩證明的功能，報告上就不宣稱做得到。

## 5. 工作項目

### P1 遊戲流程：說明頁、2 關、結束頁（G1、G10 的一部分）

**描述格式**（新增欄位；沒寫 `關卡` 時，原本的 `地圖`／`規則` 就是第一關）：

```json
{
  "標題": "峽谷裡的苦花魚",
  "說明": ["方向鍵移動苦花魚", "吃到藻類加 10 分", "碰到毒魚陷阱扣一條命"],
  "關卡": [
    { "名稱": "第一關 清澈溪流", "地圖": ["..."], "背景": "水下", "過關": "分數 >= 100" },
    { "名稱": "第二關 危險陷阱", "地圖": ["..."], "背景": "Water And Rocks", "過關": "碰到 出口" }
  ],
  "角色": { "...": "..." },
  "設定": { "生命": 3, "時間": 90 }
}
```

**編譯方式**：

- 在舞台加上 `階段` 與 `關卡` 變數，以及 `開始遊戲`、`進入關卡`、`清場`、`遊戲結束` 四個廣播。
- 把現在的 `whenFlag` 腳本改由 `進入關卡` 啟動。綠旗只負責重設狀態，然後顯示說明頁。
- 說明頁是新的 `說明` 角色（大字文字造型），按空白鍵或點擊後才廣播 `開始遊戲`。
- **沒寫 `說明` 時，從玩家行為自動產生操作說明**，例如平台移動 → 「← → 移動、↑ 跳」，子彈 → 「空白鍵發射」，
  點擊目標 → 「用滑鼠點」。這樣「開始前必須有說明」一定會成立。
- 每關有自己的地圖。`牆` 角色每關一個造型；實體分身在 `清場` 時刪除，進入下一關時依新地圖重新產生；
  實體只在出現於該關地圖的關卡裡產生。
- `過關` 條件沿用現有規則條件語法。第一關過關後顯示過場卡（關卡名稱，2 秒），再進入第二關；
  最後一關過關才是 `win`。
- 結束頁顯示「過關！／失敗」與最終分數，並提示「按綠旗再玩一次」。

**檢查**（`src/spec/check.ts`）：

- 關卡數 > 2 → 錯誤。
- 某一關沒有可達成的 `過關` 條件 → 錯誤。這條沿用現有的可達性檢查，逐關跑。
- 說明超過 6 行或單行太長 → 警告，因為說明頁會放不下。

**試玩**（`src/spec/scenario.ts`）：

- 新增 Subject `{ stage: 'backdrop' }` 和 `{ sprite, field: 'saying' }`，新增步驟 `{ kind: 'until', subject, op, value, ms }`。
- 自動劇本：
  1. 開場時說明頁可見，玩家角色還不能移動；按空白鍵後才能移動。
  2. 用 `set` 把分數設到過關門檻（或由 bot 走到終點），確認進入第二關，並且背景已換。
  3. 第二關由 bot 跑完，確認出現結束頁。

**驗收**：用 #29《苦花魚》、#4《香魚》、#12《石虎》改寫成 2 關描述，三者建置成功、自動試玩通過、競賽檢查通過。

### P2 素材：官方素材庫與自畫素材（G3、G4）

- `外觀` 可以寫內建造型（`hero` 等，維持相容），也可以寫官方素材名稱或中文關鍵字，例如 `"魚"`、`"Crab"`、
  `"官方:Duck"`。名稱用 `matchLibrarySprite`／`library-zh.ts` 解析；找不到時，feedback 列出最接近的 5 個。
- 每關或每個場景都可以寫 `背景`，用 `matchLibraryBackdrop` 解析，例如「水下」「森林」「城市」。
- 自畫素材：`"外觀": "檔案:素材/苦花.png"`，路徑相對於遊戲資料夾，例如 `output/games/<名稱>/素材/`。
  支援 PNG、SVG，大小上限 1 MB；建置時計算 md5、放進 `.sb3`。
- **授權紀錄**：匯入的檔案必須在描述的 `素材來源` 填寫 `{ "檔案": "...", "來源": "自繪｜CC BY-NC｜…", "作者": "...", "網址": "..." }`，
  沒填就建置失敗。官方素材自動標記為「Scratch 內建」。報告新增 `assets` 段落，內容沿用
  `inspectProjectAssetProvenance`。
- **下載與離線**：建置時用 `createScratchAssetFetcher` 下載素材，並做 md5 驗證，快取放在 `output/cache/assets/`。
  另外新增 `assets prefetch` 指令，讓學校網路不穩時可以先把常用素材下載好。
- **碰撞大小**：現在的物理假設造型是一格大小，素材庫造型大小不一。建置時依造型邊界設定 `size`，讓它符合一格；
  玩家另外用一個隱藏的碰撞方塊造型做碰撞判定，外觀只是顯示。這部分要有回歸測試，確保平台跳躍不會穿牆。

### P3 動畫模式：Story Spec（G2、G10）

新模組 `src/story/`，結構比照 `src/spec/`，分成 `types`、`normalize`、`check`、`compile`、`scenario`、`prompt`。
新指令 `story <描述.json> [--playtest]`，產出同樣放在 `output/games/<名稱>/`。

```json
{
  "類型": "動畫",
  "標題": "時空渡船：淡水河的故事",
  "主角": "渡船伯",
  "角色": { "渡船伯": { "外觀": "檔案:素材/渡船伯.png" }, "帆船": { "外觀": "Sailboat" } },
  "場景": [
    {
      "名稱": "清代",
      "背景": "檔案:素材/清代河港.png",
      "動作": ["帆船 從 左 移到 中間 4秒", "渡船伯 說「這些茶葉要運到大稻埕」3秒", "等 2秒"]
    },
    { "名稱": "現代", "背景": "City With Water", "過場": "淡出", "動作": ["..."] }
  ],
  "結尾": "淡水河，陪著台北長大。",
  "資料來源": ["..."]
}
```

- **動作語法**是小模型容易寫的固定句型：出現、消失、移到（位置或座標）、說／想（文字，秒數）、等、換造型、
  播放音效、旁白（片底字幕條）。解析方式比照現有的規則解析：寬容讀取，看不懂的句子回報 `→` 建議。
- **編譯**：
  - 舞台依序跑場景：換背景，然後用「廣播並等待」播出 `場景N`。各角色在收到 `場景N` 時執行自己在這一場的動作。
  - 過場用一個全螢幕遮罩角色做淡出淡入（調整 ghost 特效）。
  - 自動加片頭標題卡和片尾卡，`結尾` 文字顯示在片尾卡上。
- **片長**：每個動作的秒數都是固定的，編譯時就能精確算出總片長。不在 60–180 秒內就建置失敗，並建議要增減哪一場。
  說話的文字太長時，自動依字數延長秒數（例如每 6 個字 1 秒），或拆成兩句，避免字幕還沒讀完就消失。
- **檢查**：要有主角，而且主角至少出場一次；場景至少 2 個，而且背景不同；要有片頭和片尾。
- **試玩**：以真實時間播完整部動畫，記錄背景切換的時間點和結束廣播，與編譯時算出的片長比對（允許誤差 ±2 秒）。
  因為要播 60–180 秒，這項只在 `--playtest` 時跑，不放進單元測試；單元測試只驗證時間軸計算。

### P5 競賽規格檢查（G9）

- 新指令 `contest-check <作品.sb3> [--profile youzhi-2026] [--run]`，**對任何 `.sb3` 都能用**，包括學生手做的作品。
  - 靜態檢查（讀 `project.json`）：背景數量和換背景積木、是否有說明文字或說明角色、勝負與結束條件的線索、
    關卡變數、素材來源（沿用 `inspectProjectAssetProvenance`）。
  - `--run` 動態檢查：在預覽中執行並記錄時間軸，量測片長和過場次數；遊戲則檢查開場是否停在說明頁。
- 規則放在設定檔 `src/contest/profiles/youzhi-2026.json`，內容包括：類型、片長範圍、最少過場數、關卡上限、必要項目。
- 輸出沿用 `feedback` 格式（每行附 `→` 建議）。`spec`／`story` 建置時自動附上 `contest` 段落。
- `inspect --format markdown` 加一節「競賽規格」，讓老師批次檢查全班作品（`batch` 也會帶出這一節）。

### P6 作品說明表輔助（G11）

`report-draft <遊戲資料夾>` 產生 `output/games/<名稱>/作品說明草稿.md`：

- **素材清單**：每個素材的來源與授權，取自 P2 的紀錄。
- **生成式 AI 使用紀錄**：使用的工具、模型名稱、日期、每一輪的需求與修改，取自 `_過程/` 的報告和模型回覆。
- **創作歷程**：各版本時間軸，取自 `_過程/舊版/`。
- **河流探究紀錄**：只產生欄位標題和 `資料來源` 清單，內容留給學生填寫；工具不自動寫事實內容。

| 之後 | P4-4 捲軸、P4-5 量表                                | #4 完整版、#8／#20 部分                              |

每個階段各自是一組 commit，完成時 `npm test`、lint、build 都要通過，現有 5 個範例的試玩不能退步，
並在 `docs/guide/game-spec.md` 更新格式說明。

## 7. 風險

- **素材大小 vs. 物理**：素材庫造型大小不一，最容易讓平台跳躍出錯。P2 的碰撞方塊方案要先做實驗再全面採用。
- **說明加長會壓縮小模型能力**：分模式說明、量 token；必要時讓 `說明` 和 `背景` 都可以省略，由工具自動補上。
- **動畫試玩很慢**：一次 60–180 秒，只在 `--playtest` 和驗收基準裡跑。
- **素材下載需要網路**：學校環境可能不穩定，靠 `assets prefetch` 和快取處理；下載失敗時退回內建造型並警告。
- **中文字幕版面**：說話泡泡和說明頁的換行、字數上限要實測。
- **原創性**：工具定位是產生骨架、檢查規格、留存紀錄；P6 只產生事實性的紀錄，不替學生寫探究內容。
- **Qblock 相容**：競賽也接受 Qblock 作品，但要先確認 Qblock 能否開啟這裡產生的 `.sb3`。這項先列為待查。
